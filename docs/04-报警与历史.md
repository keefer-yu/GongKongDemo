# 报警与历史

## 1. 四限报警

每个模拟量点位可配置：

| 字段 | 含义 | 本项目示例 |
|---|---|---|
| LL | 低低限 | 液位 5% |
| L | 低限 | 液位 15%、温度 20°C |
| H | 高限 | 液位 85%、温度 80°C、压力 0.6MPa |
| HH | 高高限 | 液位 95%、温度 95°C、压力 0.8MPa |
| deadband | 恢复回差 | 温度 2°C |
| delaySeconds | 持续多久才触发 | 2 秒 |

配置在 `config/devices.json` 的 `tags[].alarm`。

## 2. 状态机

```text
            超限持续 delay
Normal ───────────────────► Active
  ▲                            │
  │                            ├── 操作员确认 ──► Acked
  │                            │
  │        恢复并离开死区        ▼
  └──────────────────────── Cleared
```

- **Active**：报警存在，未确认。
- **Acked**：操作员知道了，但报警仍然存在；数值恢复后变为 Cleared。
- **Cleared**：报警已恢复，历史保留。

代码：`Scada.Alarms/AlarmEngine.cs`。

## 3. 为什么要死区

假设温度 H=80，数值在 80.0 附近抖动：

```text
80.1 → 报警
79.9 → 恢复
80.1 → 报警
...
```

加入死区 2°C 后：

- 触发：≥ 80
- 恢复：< 78（80 - 2）

这样报警不会在阈值附近来回刷屏。

## 4. 为什么要延时

传感器尖峰、网络抖动可能造成单点超限。`delaySeconds=2` 表示连续 2 秒都超限才真正报警；中途恢复就取消。

实现用 `PendingLevel + PendingSince`，不依赖采样次数，所以扫描周期变化也成立。

## 5. 历史库

SQLite 文件：`data/v3-history.db`（V4 用 `v4-control.db`，V5 用 `v5-northbound.db`）。

### 表结构

```sql
tag_history(
  id, ts_utc, tag_id, value, quality, raw_value
)

alarm_events(
  id, ts_utc, tag_id, tag_name, level, state, value,
  message, cleared_utc, acked_utc
)

command_audit(
  id, ts_utc, source, tag_id, requested, actual, ok,
  message, duration_ms
)
```

代码：`Scada.Storage/SqliteHistoryStore.cs`。

### 写入策略

V3 在每次采集成功后写一次全量点位（8 个点 × 2Hz）。生产项目通常会：

- 批量写入 / 异步队列；
- 只写变化点（死区压缩）；
- 按时序数据库（TDengine/InfluxDB）分区；
- 设置保留期与归档。

### 查询与导出

- V3 的“历史”页：选点位、选 1/5/30 分钟、查询、导出 CSV。
- SQL 示例：

```sql
SELECT ts_utc, value FROM tag_history
WHERE tag_id='temp' AND ts_utc >= '2026-11-02T00:00:00Z'
ORDER BY ts_utc;
```

## 6. 故障注入

V3/V4/V5 的“报警”页有：

- 注入超温（温度强制 100°C）
- 注入超压（压力强制 0.82MPa）
- 注入低液位（液位强制 2%）

20 秒后自动恢复。代码在 `ReactorProcessModel.InjectFault`。

## 7. 自己试

1. 跑 V3，点“注入超温故障”。
2. 约 2 秒后出现 HH 报警。
3. 点“确认选中报警”，状态变“已确认”。
4. 等故障自动恢复，报警清除。
5. 去“历史”页查询温度，导出 CSV。
6. 用 DB Browser for SQLite 打开 `data/v3-history.db` 看三张表。
